# Hostel Management System

A full-stack Java Spring Boot + PostgreSQL + React system for running a
hostel end-to-end: login-protected admin access, onboarding students and
wardens, managing hostels and rooms, processing booking requests, and
tracking hostel fees — with a sidebar dashboard that shows live room
availability.

## 1. Folder structure

One project folder, with the two halves clearly separated:

```
hostel-management-system/
├── backend/            <-- Spring Boot + PostgreSQL (Java)
│   ├── pom.xml
│   └── src/main/...
├── frontend/            <-- React (Vite)
│   ├── package.json
│   └── src/...
├── build-frontend.sh    <-- builds frontend/ and copies it into backend/
└── README.md            <-- this file
```

`backend/` and `frontend/` are independent codebases you can open, read,
and explain separately. They're connected by one build step:
`build-frontend.sh` compiles the React app and copies the result into
`backend/src/main/resources/static/`. After that, running the backend
(`mvn spring-boot:run`) serves **both** the compiled React UI and the REST
API from the same port (`8080`) — one process, one URL, for the actual
demo. During development you can still run the frontend separately with
hot-reload (see section 8) if you want instant feedback while editing.

## 2. What the system does

- **Login required** — nobody sees any data without signing in. A default
  admin account is created automatically the first time you run the app.
- **Admin can add other users** — from the Users page, an Admin creates
  new accounts (Admin or Staff) with a username/password/role. Non-admins
  can't see or use this page — the backend enforces that with
  `hasRole("ADMIN")`, not just the UI.
- **Sidebar dashboard** — stat cards (students, wardens, hostels, rooms,
  bookings) plus a live "Hostels & Availability" panel showing every open
  hostel, its warden, and a beds-free progress bar.
- **Students** register and submit **Bookings** for a **Room**.
- **Wardens** review pending bookings and **approve** or **reject** them.
- Each **Hostel** has many **Rooms**; each **Room** belongs to one hostel and
  has a capacity, a type (SINGLE/DOUBLE/SHARED) and a live status
  (AVAILABLE/FULL/UNDER_MAINTENANCE) that updates automatically as bookings
  are approved or cancelled.
- Each **Booking** tracks a hostel fee amount and whether it has been paid.

## 4. Backend structure (`backend/src/main/java/com/hostelms/`)

```
├── HostelmsApplication.java   # main() entry point + seeds a default admin
├── model/                     # entities (the "M" - data + OOP)
│   ├── Person.java            # abstract base class
│   ├── Student.java           # extends Person
│   ├── Warden.java            # extends Person
│   ├── Hostel.java / Room.java / Booking.java
│   ├── AppUser.java           # login accounts (separate from Student/Warden)
│   └── RoomType.java / RoomStatus.java / BookingStatus.java / Role.java (enums)
├── dto/                       # request/response shapes for the REST API
├── repository/                # Spring Data JPA interfaces
├── service/                   # business logic
├── security/                  # JwtService, JwtAuthFilter, SecurityConfig
├── web/                       # SpaFallbackController (serves React on refresh)
└── controller/
    ├── AuthController.java    # POST /api/auth/login
    ├── UserController.java    # /api/users - Admin-only
    └── *ApiController.java    # /api/students, /api/hostels, /api/rooms, ...
```

`backend/src/main/resources/static/` is where the built React app lands -
generated by `build-frontend.sh`, not hand-edited.

## 6. Database design (7 tables, related)

```
persons (abstract parent table)
   ├── students   (1) ───< bookings (many)
   └── wardens    (1) ───< hostels (many, "managed by")
                  (1) ───< bookings (many, "approved by")

hostels (1) ───< rooms (many)
rooms   (1) ───< bookings (many)

app_users (standalone - login accounts, not linked to the hostel data)
```

That's **7 physical tables** built from **6 core entity classes** (Person,
Hostel, Room, Booking, AppUser, plus Person's two subclasses
Student/Warden), comfortably meeting the "at least 5" requirement.

## 7. Where the OOP concepts are

- **Inheritance**: `Person` is an abstract class. `Student` and `Warden` both
  `extends Person`, inheriting `id`, `fullName`, `email`, `phone`,
  `createdAt` and the `getRole()` contract, while adding their own fields.
  Mapped with `@Inheritance(strategy = InheritanceType.JOINED)`.
- **Polymorphism**: `getRole()` is abstract on `Person` and overridden
  differently in `Student` and `Warden`.
- **Encapsulation**: every field in every entity is `private`, reachable
  only through getters/setters. Business rules live inside the entity
  itself, e.g. `Room.hasSpace()`, `Booking.approve(Warden)`,
  `Room.refreshStatus()`. `AppUser.passwordHash` is never exposed outside
  the class, not even in JSON (`@JsonIgnore`).
- **Constructors**: each entity has a no-args constructor (required by JPA)
  and a convenience constructor for creating fully-formed objects in code.
- **Packages**: `model`, `repository`, `service`, `security`, `dto`,
  `controller` — a standard layered Spring Boot structure.

## 8. CRUD + Auth mapping

Every entity (Student, Warden, Hostel, Room, Booking) has a REST controller
under `/api/**`, all requiring a valid login:

| Action | Method | URL                                   |
|--------|--------|-----------------------------------------|
| Create | POST   | `/api/{entity}`                          |
| Read   | GET    | `/api/{entity}`, `/api/{entity}/{id}`    |
| Update | PUT    | `/api/{entity}/{id}`                     |
| Delete | DELETE | `/api/{entity}/{id}`                     |

Plus `POST /api/auth/login` (public), `GET/POST/DELETE /api/users`
(Admin only), and `POST /api/bookings/{id}/approve|reject|cancel`.

## 9. Running it locally

**Prerequisites:** JDK 17+, Maven, PostgreSQL running locally, Node.js 18+.

1. Create the database:
   ```sql
   CREATE DATABASE hostel_management;
   ```
2. Open `backend/src/main/resources/application.properties` and update
   `spring.datasource.username` / `spring.datasource.password` to match
   your local PostgreSQL setup.
3. From the project root, build the frontend into the backend (once, or
   whenever you change frontend code):
   ```bash
   ./build-frontend.sh
   ```
   (On Windows: `cd frontend`, `npm install`, `npm run build`, then copy
   `dist/*` into `backend/src/main/resources/static`.)
4. Run the backend:
   ```bash
   cd backend
   mvn spring-boot:run
   ```
5. Visit **http://localhost:8080** — serves the React UI *and* the API
   (`/api/...`) together.

A default admin login is created automatically the first time the app
starts against an empty database:
```
username: admin
password: admin123
```

## 10. Optional: frontend hot-reload during development

If you're actively editing React code and want instant reload instead of
rebuilding every time:
```bash
cd frontend
npm install
npm run dev
```
Visit `http://localhost:5173` instead — Vite's dev server proxies `/api`
calls to your already-running backend on `:8080` (see the `proxy` setting
in `frontend/vite.config.js`), so login and every other feature works the
same way. This is purely a development convenience; for the actual
submission/demo, section 9 above (one command, one port) is what to use.

## 11. Suggested demo flow for your lecturer

1. Run the backend (`cd backend && mvn spring-boot:run`), open
   **http://localhost:8080**, log in as `admin` / `admin123`.
2. Go to **Users**, add a Staff account for someone else — point out that
   this page (and its API endpoint) only works for Admins.
3. Add a Warden, then a Hostel (assign that warden), then a Room inside it
   (capacity 2, type DOUBLE), then a Student.
4. Create a Booking for that student in that room → status starts `PENDING`.
5. Go to Bookings, pick the warden, click **Approve** → status becomes
   `APPROVED` and the room's occupant count/status updates on the dashboard.
6. Try adding one more booking than the room's capacity allows → the
   system rejects it with a clear error (`Room.hasSpace()` business rule).
7. Log out, and show that calling `/api/students` without a token returns
   401 (e.g. via a browser's dev tools or Postman) — proving the API
   itself is protected, not just the React screens.

This flow touches every CRUD operation, the inheritance hierarchy, a real
business rule enforced inside the entity, and the authentication/
authorization layer — everything a lecturer would plausibly ask you to
explain or reconstruct.
